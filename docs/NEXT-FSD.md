# Next.js / App Router / Feature-Sliced Design

Фронтенд работает на Next.js 16 и React 19. Корень приложения — эта папка,
а не корень внешнего проекта `nstore` с инструментами аудита.

## Запуск

Нужен Node.js 22.14+. Выполните `npm ci`, скопируйте `.env.example` в
`.env.local`, заполните настройки и выполните `npm run dev`.
Production: `npm run build`, затем `npm start`.

Источники данных:

- `NEXT_PUBLIC_CATALOG_SOURCE=django`: Django из соседней папки `backend`.
  `DJANGO_API_ORIGIN=http://127.0.0.1:8000` — серверный адрес для проксирования
  `/api/v1/*`. `NEXT_PUBLIC_DJANGO_API_URL` обычно оставляется пустым: браузер
  работает с API через тот же origin, сохраняя сессию и CSRF.
- `NEXT_PUBLIC_CATALOG_SOURCE=supabase`: существующие публичные Supabase URL и
  anon key. CRM, кабинет и редакционные данные пока используют существующий
  Supabase API, как до переноса. Миграция этих API на Django — отдельная задача.
- `NEXT_PUBLIC_CATALOG_SOURCE=demo`: синтетический каталог без внешних сервисов.
  По умолчанию гость; `/shop?client=1` включает демонстрационный B2B-профиль.

Все бывшие `VITE_*` переменные переименованы в `NEXT_PUBLIC_*`. Они встраиваются
в клиент при сборке: после смены требуется новая сборка. Секретные ключи остаются
серверными переменными без этого префикса. Публичная серверная карточка товара
запрашивает только анонимные цены; персональные цены получает браузер по сессии.

## Слои

```text
app/                    Next: page, layout, loading, error, not-found, Route Handlers
src/
  app/                  провайдеры и глобальные стили
  views/                слой pages: магазин, товар, CRM, кабинет, публичные страницы
  widgets/              составные блоки: лендинг, товар, статическая страница
  features/             shopping, auth, смена языка, настройки, PWA
  entities/             catalog, content, order, session
  shared/               API transport, i18n, UI, форматирование, навигация
```

`views` — имя FSD-слоя Pages, выбранное намеренно: `src/pages` зарезервирован
Next.js для Pages Router. Одновременного второго роутера и SPA catch-all нет.
В `app` находятся тонкие файлы маршрутов, бизнес-логика — в FSD.

Каждый слайс имеет `index.ts` — публичный API. Внешние потребители обращаются
через него; внутренние файлы могут обращаться к сегментам своего слайса.
Серверные функции каталога экспортируются отдельно из `entities/catalog/server.ts`
с `server-only`, чтобы не попасть в клиентский граф зависимостей.

Импорты направлены вниз: app → views → widgets → features → entities → shared.
Между слайсами одного слоя импортов нет. `npm run check:architecture` проверяет
направления импортов, публичные API и отсутствие зависимостей от Vite/React Router.

`shopping` объединяет каталог покупателя, корзину, избранное и оформление заказа:
эти действия используют общие данные покупателя и расчёт цены. Чистые правила
каталога (нормализация, группировка, поиск, цены) находятся в `entities/catalog`.
Существующая бизнес-логика CRM и кабинета сохранена внутри соответствующих
слайсов Pages; разбиение каждой вкладки на отдельные доменные фичи не требуется
для границ между слоями и может выполняться по мере изменения этих разделов.

## Маршруты товаров

- `/product/[slug]` — полноценная серверная страница товара. Сохранён существующий
  формат slug с артикулом для совместимости со старыми ссылками.
- Заголовок, описание, canonical, Open Graph и JSON-LD товара формирует сервер.
  Неизвестный товар вызывает `notFound()`, сбой API — экран ошибки с повтором.
- Варианты, избранное и корзина работают на странице, без товарного overlay/dialog.
  Кнопка добавления не закрывает страницу. Ссылку можно открыть в новой вкладке.
- `/shop?p=<id>` переводит на страницу товара после определения ID в каталоге.
- 812 прежних редиректов сохранены в `migration/next-redirects.json` и подключены
  через Next config. `/opt` сохранён отдельной страницей оптового прайса с поиском,
  фильтром раздела и тремя колонками цен; закрытые цены доступны по договору.
- Главная, поиск, категории и магазин используют один источник товаров и одну
  корзину. Корзина и избранное сохраняются между маршрутами и перезагрузками.

Оболочка CRM перенесена в `app/crm/layout.tsx`; вкладки — отдельные `page.tsx`.
Проверка ролей сохранена. Клиентский AuthGuard управляет интерфейсом;
разрешения на данные по-прежнему проверяют RLS/Supabase или Django API.

PWA больше не кеширует SPA HTML, RSC-ответы или приватные API. Новый service worker
удаляет старые nstore-кеши, а при отсутствии сети показывает `offline.html`.
Старый Edge endpoint аналитики перенесён в `app/api/track/route.ts`.

## Проверки

```text
npm run typecheck
npm run check:architecture
npm run build
npm run test:checkout
npm run test:catalog
npm run test:browser
```

Для browser-проверки соберите приложение с `NEXT_PUBLIC_CATALOG_SOURCE=demo`
и запустите на порту 3100 (`npm start -- --port 3100`; в PowerShell при проблемах
передачи аргументов: `node node_modules/next/dist/bin/next start -p 3100`).
`TEST_ORIGIN` позволяет использовать другой адрес. Нужен Chrome/Edge; путь можно
задать через `CHROME_PATH`. Проверяются отдельная карточка, серверный HTML и
JSON-LD, сохранение корзины, мобильная ширина, старые ссылки и guards.
Скриншоты записываются в игнорируемую `.next/qa/`.

Проверки используют синтетические данные. Операции с реальными заказами,
1С, платежами и внешней отправкой сообщений автоматически не выполняются.
